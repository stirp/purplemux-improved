# Codex 消息未确认与后续排队停滞排查

## 用户原始需求

“有时候 codex 会话里说一遍以后，没有进入对应的 codexsession 里，状态也没有显示 agent 执行中的红色停止按钮；但是再发消息，消息却留在消息框里，状态是排队中。排查一下这里的问题是什么。”

后续补充：“看起来确实不积压，但是消息丢失了。今天发生了一次，现在并没有复现。”因此排查重点包括已发生的单次消息丢失，不能用当前队列无积压排除故障。

后续追问：“现在每次输入消息发送以后，等到其上屏都需要很久时间，这中间的时间哪儿去了？怎么能让这块感觉更连贯？”本轮继续定位上屏前延迟，并提出连续反馈的交互建议。

## 范围与约定

- 本次排查 Web 入队、终端投递、Codex 状态事件及停止按钮展示的关联。
- 通过现有代码的可控复现区分确定性缺陷与尚待现场证据的触发因素。
- 对照当天 Web 输入历史与 Codex 原生用户消息，考虑历史去重和会话留存限制，不将正文匹配等同于每次发送成功。
- 用发送历史、原生 task_started/用户消息时间戳和 Codex 诊断日志拆分延迟；区分已测耗时、源码定时参数和没有采集的浏览器渲染耗时。
- 前三轮仅诊断。本轮用户补充实际看到 TUI 留着可编辑旧正文、真正发送正文丢失，重发排队而立即发送可用，并同意使用“假写”改善上屏。本轮进入实现，不向运行中的用户会话注入诊断消息。

## 本轮修复约定

- 替代队列基线中 Codex 将终端命令完成当作投递成功的实现：发送后的消息继续保留，必须匹配本次尝试之后、当前原生会话中的用户消息，才移出待发队列。busy、工具事件、旧同文消息不单独作为接收依据。
- 使用独立于浏览器挂载的服务端确认；最长等待 30 秒，超时显示未确认错误并保留正文和附件，不自动再次粘贴。超时后每 5 秒只读检查迟到回执，确认后恢复队列；显式重试也先核对迟到记录，再决定是否投递。
- 保持每 Tab 串行，验证发送期间会话身份，未确认时后续消息不会自动覆盖或拼接到终端。暂不主动清除终端中用户可编辑草稿；真实历史触发点未复现时不宣称已定位全部原因。
- 发送前检查 Codex TUI 可输入证据，无法确认时保留消息并反馈；不把 shell 或不可输入界面当作可用会话。
- 桌面和移动端普通发送立即显示带发送状态的待确认气泡；入队请求失败保留输入草稿并撤销对应占位。确认消息原位替换，普通发送不使用 1 秒自动淡出；取消队列项同步移除对应待确认气泡。
- 已有 pending 匹配增加发送身份与时间约束，防止重连时旧同文消息消耗新占位；附件正文和图片分别匹配，不使用任意附件占位匹配任意新消息。
- Claude 终端投递及立即问题回答语义维持基线；不修改 Codex 插件、网络和用户配置，也不承诺消除 CLI 内部的准备耗时。
- 队列本次继续采用已有进程内存生命周期；服务重启后的持久恢复不在本轮范围。

## 验收标准

1. 定位首条消息移出队列和后续消息阻塞的条件，关联状态显示依据。
2. 运行相关既有测试，并验证终端写入成功但没有执行事件时的行为。
3. 记录运行现场的可观测范围、未确认事项和后续修复方向，不将模拟结果当作真实 Codex 故障复现。
4. 模拟终端写入成功但没有新用户记录：原消息和附件保留，30 秒后出现未确认提示，后续消息不自动发送。
5. 匹配记录到来才完成投递；旧记录、不相关正文、切换会话不能确认；重试能识别迟到回执而不重复粘贴。
6. UI 验证立即占位、请求失败、取消、长时间等待、同文消息和重新初始化确认，确认后只显示一份正文。
7. 执行相关回归、完整 TypeScript、改动文件 ESLint，按影响执行构建或浏览器检查并如实记录限制。
8. 超时检查或显式重试重建解析器时，查找到本次尝试的时间边界；即使迟到消息之后已有其他轮次，也不能漏报并重复投递。
9. 优先使用当前 Tab 已绑定且通过原生 session_meta 身份校验的 transcript 路径；创建超过 30 天的活动会话仍可确认，路径指向其他会话时不能确认。
10. Claude 的 base64 图片使用上传内容的摘要匹配附件身份；同文不同图不能确认，原生记录与队列快照乱序到达也只展示一个气泡。
11. 重连保留已消费原生回执与队列 ID 的对应关系，两条同文消息不能被同一条回执确认。
12. 队列快照明确携带取消结果；其他客户端和重连客户端移除已取消占位，成功出队仍等待原生记录确认，不能因空队列而直接删除。
13. Codex 图片身份验证成功后，正文匹配兼容原生前缀 `[Image #1]`（多图按顺序编号），包含纯图片输入；不改写展示正文，不删除用户正文中的字面标记，不放宽图片身份或普通文本匹配。
14. 替代客户端以 createdAt 确认队列消息的条件：只能使用服务端投递尝试时间。尚未尝试投递的消息不能被任何原生记录确认，包括刷新、无缓存新客户端及 init/append/快照乱序；没有尝试元数据的旧快照保持待确认，不回退到入队时间。
15. 服务端快照保留已开始尝试的消息 ID 与时间，成功出队后也继续提供；正文不额外留存。该元数据与队列采用同一进程生命周期，Tab 消失后清理。桌面和移动端同步投递边界；记录早于尝试时间时不能确认，记录或尝试元数据后到时应原位合并。
16. PR #79 取消竞态：DELETE 请求成功不代表消息已取消，待确认气泡只随服务端 `canceledIds` 移除。如果上次轮询后服务端已经开始投递并拒绝取消，即使 API 返回 200，也保留气泡直到真实回执确认。
17. PR #79 CI 修复：标签排序测试在弹窗初始焦点完成后操作真实 KeyboardSensor，保留焦点、拖拽与冲突断言；会话删除存储测试隔离真实日志 transport，模拟文件路径不能写入宿主文件系统。仅修正测试时序和隔离，不改变关联标签浏览、删除规格中的产品行为，不以降低断言、全局串行或自动重试规避失败。执行标准 `pnpm lint`、完整类型检查及 `pnpm test`（含 CLI）。
