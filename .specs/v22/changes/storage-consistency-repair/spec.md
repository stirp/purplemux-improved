# 存储一致性检查与修复

## 原始需求

“检查purplemux的存储文件, 看看是不是有一些数据不一致,修复问题”。

后续确认：对代码目录已不存在的“会话的分类目前很固定，增加用户自定义的能力”工作区，选择“保留历史会话，恢复代码目录”。按既有本地分支恢复代码及工作区入口；不执行原生会话删除。已被应用删除且没有可恢复文件的历史如实报告，不伪造会话记录。

## 范围与行为

- 检查本机 `~/.purplemux` 的 JSON 可解析性、工作区/分组/布局引用、会话索引及隐藏标记、原生会话文件、worktree 元数据和删除进度。
- 保留基线的历史会话导航、关闭 Tab 不等于删除会话、删除标记防复活及失败可重试语义。历史 Tab 绑定本身不视为损坏。
- 修正布局入口：已不存在的工作区返回 404，不再因读取布局重建目录及终端；有效空工作区仍可恢复默认布局。
- 修正工作区删除的锁顺序：原生会话清理可调用工作区索引清理，不得在持有工作区写锁时再次等待同一锁。删除操作独立串行，清理后重新读取最新工作区数据，保留期间的其他修改；再次核对运行终端后移除工作区，删除当前工作区时同步激活引用。
- 实际数据修复先生成可复核计划和完整受影响文件备份；对未索引且没有运行终端的单布局目录采用归档，非空业务数据或仍有终端的目录保留并报告。
- 同步已经存在的隐藏标记与删除标记，清除已明确删除的会话索引和人工状态。原生文件（含归档）不存在、无活动 Tab、无历史轮次、无人工状态/标题/标签的会话索引可在备份后清除；其余缺失原生文件的会话仅报告，不猜测删除。
- 对已不存在且不再被工作区引用的 worktree 元数据保留备份后清除。缺失代码目录或中断的原生删除计划依用户选择处理，不自动删除原生会话或修改 Git 分支。
- 写入前检查运行服务和快照；避免与服务并发覆盖，采用原子文件替换。真实数据写入需要工作区外的文件访问权限。

## 验收

1. 不存在的工作区布局 GET 返回 404，无布局/终端创建；有效工作区仍传递默认目录。
2. 工作区删除可完成会话索引清理，无锁自等待；并发更新和已保存删除标记不被旧快照覆盖，失败保留可重试工作区。
3. 逐项记录实际发现、备份、修复及保留项，重新检查 JSON 和关联引用。
4. 运行相关回归、完整 TypeScript 和改动文件 ESLint；记录未执行的构建、浏览器及部署验证。
