# 本机 Codex 与 Claude Code 进程管理及会话接入

## 原始需求

“我希望这个 purplemux 能对运行中的 codex 和 cluade 做管理，对于同一台电脑上的 codex 和 claude 进程可以进行管理，如果可能，还可以一键将独立在电脑终端启动的 codex 或 claude 进程及其运行目录接入工作区管理。”

用户确认外部接入采用：“希望停止原进程后，在工作区恢复会话”。

## 范围与边界

- 新增设置中的「本机进程」入口，桌面与移动端共享。扫描的是服务端所在机器、当前系统用户的进程，支持 Linux/macOS；不扫描其他电脑或其他用户。
- 展示代理、PID、启动时间、工作目录、来源及工作区；可刷新、搜索、打开已管理工作区、确认后停止进程或接入外部会话。
- 复用 process-utils 作为唯一系统进程查询入口，复用 tmux 的全 pane 查询和布局判断归属；识别实际可执行文件及已知 Node CLI 包装器，不因提示词出现 codex/claude 而误判。不展示命令参数、环境变量或提示词。
- 接入先可靠确定 PID 对应的原生会话 ID（打开的原生会话文件、Claude PID 注册文件或明确的 resume 参数），有歧义、文件不可读、自定义会话根不兼容时禁用；禁止按相同目录的最新会话猜测。
- 一键接入在确认框中明确中断原终端的风险。校验身份、目录、会话文件及安装可用性，准备持久化工作区/终端后向原进程发送 SIGTERM；确认退出后才恢复。退出检查窗口约 10 秒（单次系统查询存在耗时），超时则保留原进程并报错，不升级为 SIGKILL，不杀父 shell、进程组或其他任务。
- 原进程 PID 与启动时间共同作为身份，操作前重新核对当前用户和代理类型；失效或 PID 复用拒绝操作。已由本应用管理的进程只能打开工作区或停止，不重复迁入。
- 复用目录相同的工作区，新增独立终端；无对应工作区时创建。恢复复用 provider 的命令构建与状态注册，沿用应用配置，不复制原进程环境或命令参数。对话历史可恢复，内存状态、正在执行的工具和终端滚屏不保证保留。
- 接入记录持久化在 workspaces.json 的工作区字段，保存原进程身份、会话、目标终端及阶段；失败和重启后可重试。准备阶段目标是普通终端，原进程退出前不绑定可自动恢复的 Agent 会话。重复请求串行并复用目标，不重复发送已成功的恢复命令。
- 发送前持久化 dispatching 阶段；tmux 回应丢失或发送中服务退出时，不能判断命令是否已经执行，重试不得再次发送。可打开目标终端处理启动提示；重新识别到同一会话后重试完成绑定。目标终端被手动移除或发送状态仍不明确时，报告需人工恢复，不自动创建第二份会话。
- 删除工作区沿用原语义；未迁入的外部进程不因目录相同而被工作区删除操作终止。
- 本增量新增进程管理能力，不替代已有会话状态、人工工作状态、正常启动/恢复及工作区删除条款；不做任意 PTY 无损转移、跨 tmux 服务搬迁或会话 ID 猜测。

## 验收标准

PR #71 修正：原进程退出后，在持久化 dispatching 前重新读取目标布局、tmux pane PID、前台 shell、工作目录及最近输入。等待期间目标被使用、替换、移除或目录变化时不投递，保留 stopped 阶段以便显式重试。dispatching 保存后、实际发送前再次核验；明确未发送的校验失败可恢复 stopped，真正发送结果不明确仍保留 dispatching。

1. 同用户的原生/Node 包装 Codex、Claude 被识别，提示词、shell、其他用户、包装器重复记录被排除；嵌套进程归属准确。
2. 桌面/移动设置入口可用；加载、空列表、失败、刷新、搜索、未知目录/会话及操作中状态明确，失败不被显示为成功。
3. 原生会话身份可靠且唯一才允许接入；相同目录多进程不串会话。
4. 接入准备失败不停止原进程；停止超时不恢复；停止后失败保留会话和目标可重试；PID 复用、并发重复请求不误杀或重复启动。
5. 接入工作区及终端持久化，恢复使用原会话 ID 和目录；原终端退出在先，目标恢复在后。用户确认后才执行停止或接入。
6. 执行相关单元测试、完整 TypeScript、改动文件 ESLint，以及构建或浏览器验证；如实记录实机迁入及 macOS 验证限制。

### 停止操作跨域误判修正

用户反馈：“现在在管理会话的时候，我去停止其他会话，会提示跨域异常”。

- 停止/接入请求不得因反向代理改写 Host 而误判为跨站。桌面与移动端共用请求增加 `X-Purplemux-Process-Action: 1`，服务端以该非简单请求头作为同源浏览器调用证明；接口继续不开放 CORS，跨源脚本无法通过预检，跨站表单不能设置此头。
- 浏览器明确标记 `Sec-Fetch-Site: cross-site` 或 `same-site` 的跨源写入仍返回 403，即使携带上述请求头也不执行。浏览器标记 `same-origin` 时兼容未更新页面；没有该标记或自定义头的旧客户端仍按 Origin 与 Host 校验，无 Origin 的已认证 CLI 请求保持兼容。
- 不信任任意 `X-Forwarded-Host` 作为授权依据；非法/不透明 Origin 在回退校验中返回 403，不抛出 500。
- 同一防护复用于闲置页签回收与策略保存；不改变确认、身份重检、停止信号及状态语义。
- 验证代理 Host 不同下的 stop/adopt、无 Fetch Metadata 的 HTTP 访问、旧页面同源请求、真实跨站/同站跨源拒绝和错误 Origin；所有进程操作使用 mock，不停止真实会话。
